# Design Coroner — "이 디자인 시스템, 진짜 만들어야 하나?" (design-or-use)

> **호출법 — Haiku 등 하위 모델에서는 `/design-coroner`로 직접 호출하세요. 자동 발동은 모델 티어에
> 의존합니다.** 실측(2026-08-29): Haiku는 원문 프롬프트로 이 스킬을 발동하지 않고 곧바로
> 공수·비용을 추정했다(스킬이 금지한 행위). 명시 호출하면 발동한다 — 로딩 문제가 아니라
> 배차 문제이므로, 호출을 사람이 대신 해주면 해소된다.
>
> **판정 규율은 그와 별개로 티어 의존적이다.** 하위 티어 모델은 이 지침을 읽고도 검색 없이
> "없다"고 단정하고, 하지 않은 확인을 했다고 쓴다. 실측: Haiku 4.5 부재단정 40%(10런) vs
> Opus 5 0%(5런) — `docs/run-ledger.md`. 판정문을 남에게 건넬 생각이라면 Opus·Sonnet 급에서
> 실행하고 rigor 훅을 함께 켜라 — 훅은 스킬이 발동한 뒤에만 작동하므로, 직접 호출이 먼저다.

coroner(build-or-use)의 도메인 이식판. 절차는 동일하되 소스 계층·판정 어휘·검증 항목을
디자인 도메인으로 재작성했다. 원칙 승계: 검색 실패 ≠ 부재 / 검증 없는 "해결" 금지 /
공수·점수 정량화 금지 / 아이디어(시스템 구축안)를 죽일 수 있어야 함 / 기각은 상속으로.

## Step 0~1. 판정 단위 규율 + 전제 확정

build-or-use v3와 동일 (연속 판정 시 탐색 리셋, 수사의문문도 완전한 판정 요청).
추가로 반드시 확정할 전제:
- **범위**: 컴포넌트 1개인가, 카테고리(폼/네비게이션)인가, 시스템 전체인가 — 판정 단위가 다르다
- **소비자**: 디자이너 전용(Figma만)인가, 개발자 동반(코드 컴포넌트 페어 필요)인가
- **브랜드 제약**: 기존 브랜드 가이드가 있는가, 백지인가

## Step 2. 분해

시스템 구축안을 독립 단위로 쪼갠다: 파운데이션(색·타이포·간격·그리드 토큰) /
컴포넌트 인벤토리(실제 제품 화면에서 필요한 것만 — 상상 목록 금지) /
패턴(폼 검증, 빈 상태, 로딩) / 문서·거버넌스(기여 규칙, 변형 정책) / 코드 페어 여부.

## Step 3. 소스 계층 탐색 (도메인 재작성)

- **A. 플랫폼·도구 네이티브**: Figma variables·styles·컴포넌트 속성·Auto Layout,
  iOS HIG / Material 플랫폼 기본. "Figma가 원래 해주는 것"을 만들지 않는다.
- **B. 오픈소스 디자인 시스템**: Material 3, Ant, Polaris, Carbon, Primer, Fluent,
  Radix/shadcn(코드 측), 국내 사례(검색 필수 — 기억 금지). 이들은 커스텀되라고 만들어진
  가변 인공물이다 — 토큰 테마잉이 1급 기능인지가 핵심 확인 항목.
- **C. Figma Community·토큰 생태계**: Community 파일/UI kit, Tokens Studio 등
  토큰 라이브러리, 관련 플러그인. 카탈로그(Community) 빈 결과 시 웹 검색으로 확대 —
  escalation 의무 동일. 라이선스: 무료 파일 = CC BY 4.0 (상업 사용 가능하나 **원작자 표시 의무**,
  public domain 아님), 유료 파일 = 재판매·재배포 금지 — 판정문에 attribution 요건을 명시할 것.
- **D. 유료 UI kit·템플릿**: Untitled UI 류. 좌석 수·재배포 제한이 흔하므로 라이선스 확인 필수.

어휘 2계열: 디자이너 표현("무드보드", "버튼 셋")과 시스템 용어("token", "variant",
"primitive") 각각 최소 1회. 생태계 사실(어떤 시스템이 뭘 지원하는지)은 기억 금지·검색 의무.

## Step 4. 검증 (도메인 체크리스트)

- 토큰 구조가 우리 브랜드 축(색 스케일, 다크모드, 밀도)을 담을 수 있는가 — 문서로 확인
- 접근성: WCAG 대비·포커스·터치 타겟이 시스템 수준에서 보장되는가
- 코드 페어: 디자인-코드 동기 수단이 있는가 (개발자 동반 전제일 때)
- 유지보수: 최근 릴리스, 커뮤니티 활성
- 라이선스: 상용 사용 가능 여부
- **가변성 × gap 깊이** (승계): 표면 gap(토큰 교체로 해결 — 색·타이포·라운딩) vs
  심층 gap(브랜드 고유 인터랙션·도메인 특수 컴포넌트 — 재작성 필요)

## Step 5. Coverage 판정

각 단위를 해결 / 부분 / 미해결 / 확인 불가 / **사용 테스트 필요**(미감·손맛은 문서로
판정 불가 — 후보 2개로 실제 화면 1개씩 조립 후 재판정) / **거버넌스로 해결**(신규) 중 분류.

"거버넌스로 해결"은 gap의 본질이 컴포넌트 부재가 아니라 정책 부재(변형 난립, 기여 규칙
없음, 채택 저조)일 때 쓴다. 디자인 시스템의 지배적 실패 원인은 구현이 아니라 거버넌스임이
정설이므로, 이 상태가 다수면 "만들기"가 아니라 "규칙 세우기"가 답이라고 조기 선언한다.

## Step 6. 판정 — 도메인 정착 어휘 차용

- **Adopt (그대로 채택)**: 기존 시스템 + 표면 토큰 교체로 충분
- **Adapt (커스텀)**: 기존 시스템 기반 + 심층 gap 컴포넌트만 확장. 변형 추가는
  근거(사용 사례 + 재사용 가능성) 있을 때만 — 기존 거버넌스 문헌의 규칙을 차용
- **Create component (부분 신규)**: 특정 컴포넌트/패턴만 신규 — 이슈 단위로 명세
- **Create system (전체 신규)**: 브랜드 제약·플랫폼·라이선스가 기존 전부와 충돌할 때만.
  이 판정에는 반대 논거 1개 이상 의무

판정 후 **레퍼런스 팩** 동봉: 채택하지 않는 시스템에서도 차용할 것(네이밍 체계, 토큰
구조, 문서 형식)을 목록화 — 기각은 상속이다.

## 출력·태그·금지

build-or-use v3와 동일: provenance 태그(태그 정직 조항 포함 — 검색 없는 [WEB] 부착 금지),
정량화 금지, 검증 없는 "해결" 금지, failure log 필수. 지시서가 필요하면 executor로
연결 (Adapt/Create 판정의 gap 항목이 이슈가 된다).
